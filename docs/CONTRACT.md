# Контракт: сайт, бот и AI-ядро «Злой инвестор» (T25)

Версия **1.0** от 06.11.2026. Утверждает ведущий (Влад). Меняется только через задачу в `TASKS.md`
и запись в «Журнале решений»; несовместимое изменение — новая версия этого файла.

Основа — временная схема Ivan-Claude (`bot/src/api/http.mjs`) и сценарий Ратмир-Claude
(`docs/BOT_SCENARIO.md`). Всё из временной схемы осталось на месте, новое только добавлено:
бот T27 продолжает работать, нужно лишь дописать поля, которые он хочет показывать.

## 1. Кто с кем говорит

```
 студент ── браузер ──► https://fightinvestor.ru ── Caddy ──┬─ /      → статика сайта (T26)
                                                            └─ /api/* → API 127.0.0.1:8080 (T28)
 студент ── Telegram ──► бот (T27) ── http://127.0.0.1:8080 ─────────► тот же API
                                                                       └─► Gemini (T22), ключ только тут
```

- **Один сервер** `BOT_SERVER_HOST` (см. `docs/BOT_SERVER.md`): Caddy (HTTPS для `fightinvestor.ru`),
  API (T28), бот (T27). Сайт и API на одном домене, поэтому CORS не нужен.
- **API — единственное место с логикой**: вопросы, оценка, советы, проверки, хранение. Сайт и бот
  только показывают то, что вернул API, и ничего не считают сами.
- **Ключ Gemini и токен Telegram** — только в окружении сервера и в Actions Secrets. В браузер,
  в Git и в журналы не попадают.

## 3. Порядок работы студента

1. `GET /api/persona` — карточка инвестора для первого экрана.
2. `POST /api/sessions` — питч. API проверяет его, возвращает **факты из питча** («что я понял»)
   и **сразу первый вопрос**. Клиент может сначала показать факты с кнопками «Всё верно» и
   «Поправить питч» (тогда снова `POST /api/sessions`), а может сразу показать вопрос.
3. `POST /api/sessions/{id}/answers` × 5 — ответы. После ответов 1–4 приходит следующий вопрос,
   после 5-го — итог: оценка и 3 совета.
4. Второй раунд — снова `POST /api/sessions` с `previousSessionId`. В итоге будет «было → стало».

`GET /api/sessions/{id}` возвращает текущее состояние: после перезагрузки страницы или
перезапуска бота студент продолжает с того же места.

## 4. Операции

Все тела запросов и ответов — JSON в UTF-8. Тексты для людей — на русском.

### `GET /api/health`

`200 {"ok": true, "mode": "live" | "demo", "version": "1.0"}`. `demo` — ключа модели нет или
включён `DEMO_MODE=1`, ответы берутся из заготовок.

### `GET /api/persona`

`200 Persona` (тип ниже). Пока персонаж не выбран по жеребьёвке (T29), отдаётся условный
бизнес-ангел из `docs/BOT_SCENARIO.md`.

### `POST /api/sessions` — начать раунд

Запрос:

```json
{ "userId": "web:7f1c…", "pitch": "текст питча", "previousSessionId": null }
```

- `userId` — обязателен (см. раздел 6).
- `pitch` — 1–4000 символов после обрезки пробелов.
- `previousSessionId` — необязателен: id прошлой сессии **того же** `userId` для второго раунда.

Ответ `201 Step` с `step: 1` и полем `facts`. Пример: `contract/examples/start.json`.

### `POST /api/sessions/{sessionId}/answers` — ответить на вопрос

Запрос:

```json
{ "userId": "web:7f1c…", "step": 1, "answer": "текст ответа" }
```

- `step` — номер вопроса, на который отвечают (1–5). Защищает от двойной отправки, присылайте его.
  Без `step` ответ засчитывается в текущий вопрос, как во временной схеме бота, но без этой защиты.
- `answer` — 1–2000 символов. «Не знаю ответа» — обычный ответ текстом.

Ответ `200`:
- после шагов 1–4 — `Step` со следующим вопросом (`contract/examples/answer.json`);
- после шага 5 — `Done` с оценкой и советами (`contract/examples/done.json`).

**Повтор того же запроса** (тот же `step`, ответ уже принят) возвращает тот же результат,
что и в первый раз, и ничего не меняет. Это делает безопасной кнопку «Повторить» после сбоя сети.

### `GET /api/sessions/{sessionId}?userId=…` — текущее состояние

`200 Step` (если раунд идёт) или `200 Done` (если закончен).

### `DELETE /api/users/{userId}` — удалить мои данные

`204`. Удаляет все сессии пользователя (команда бота `/delete`). Желательно, не блокирует демо.

## 5. Типы

```ts
type Persona = {
  id: string;                 // "angel"
  name: string;               // "Олег"
  title: string;              // "Бизнес-ангел"
  intro: string;              // 2–4 предложения для первого экрана
  howScored: string;          // как ставится оценка, 2–4 предложения
};

type Facts = {
  known: string[];            // что взято из питча, с цифрами как в питче
  missing: string[];          // чего не хватает
};

type Step = {
  sessionId: string;          // UUID
  round: number;              // 1, 2, …
  status: "in_progress";
  step: number;               // 1..5 — номер текущего вопроса
  totalSteps: 5;
  question: string;           // текст вопроса
  topic: string;              // "Клиент" | "Доказательства" | "Деньги" | "Конкуренты" | тема персонажа
  reaction: string | null;    // короткая реакция на прошлый ответ, без балла (null на шаге 1)
  facts?: Facts;              // только в ответе на POST /api/sessions и в GET
  notice: string | null;      // одна фраза о попытке выпросить балл и т. п.; показать перед вопросом
  demo: boolean;              // true — ответ из заготовки, а не от модели
};

type Criterion = {
  id: number;                 // 1..10, порядок как в кейсе
  name: string;               // "Реалистичность решения проблемы"
  level: 0 | 1 | 2 | 3;       // 0 нет данных, 1 заявлено, 2 есть цифры, 3 подтверждено
  weight: number;             // вес персонажа, сумма весов = 100
  score: number;              // weight × level / 3, округлено до 0,1
  max: number;                // = weight
  evidence: string | null;    // цитата из питча или ответа; null только при level 0
  comment: string;            // одна фраза «за что»
};

type Advice = {
  text: string;               // готовый текст совета целиком — клиенту достаточно показать его
  action: string;             // что сделать (глагол + объект)
  deadline: string;           // "сегодня" | "за 2 дня" | "до пятницы" — не дольше недели
  doneWhen: string;           // признак «готово»
  basedOn: string;            // "вопрос 3" | "критерий 4"
};

type Result = {
  criteria: Criterion[];      // ровно 10
  total: number;              // сумма score, округлено до целого, 0..100
  max: 100;
  summary: { strong: string; weak: string };
  advice: Advice[];           // ровно 3
  previousTotal: number | null; // итог прошлого раунда, если это второй раунд
};

type Done = {
  sessionId: string;
  round: number;
  status: "done";
  done: true;
  result: Result;
  demo: boolean;
};

type ApiErrorBody = {
  error: {
    code: ErrorCode;
    message: string;          // можно показать пользователю как есть
    missing?: string[];       // для EMPTY_PITCH: чего не хватает в питче
    retryAfterSec?: number;   // для RATE_LIMITED
  };
};
```

**Совместимость с временной схемой бота:** поля `sessionId`, `step`, `totalSteps`, `question`,
`done`, `result.criteria[].name/score/max/comment`, `result.total`, `result.max` остались прежними.
Изменилось одно: `result.advice` теперь массив объектов, а не строк — показывайте `advice[i].text`.

## 6. Пользователи и изоляция

- `userId` присылает клиент: бот — `tg:<Telegram user id>`, сайт — `web:<UUID>`, который браузер
  создаёт один раз и хранит в `localStorage`. Формат: `^(tg|web):[A-Za-z0-9-]{1,64}$`.
- Сессия принадлежит `userId`, который её создал. Чужой `userId` или несуществующий `sessionId` —
  одинаковый ответ `404 SESSION_NOT_FOUND`, чтобы нельзя было проверить, существует ли сессия.
- `sessionId` — случайный UUID v4, не номер по порядку.

## 7. Ошибки

| HTTP | `code` | Когда | Что делает клиент |
|---|---|---|---|
| 400 | `BAD_REQUEST` | Нет обязательного поля, неверный JSON или `userId` | Это баг клиента, показать общую ошибку |
| 422 | `EMPTY_PITCH` | Пустой питч, «см. презентацию», нет сути. В `missing` — чего не хватает | Показать `message` и `missing`, попросить питч заново |
| 422 | `NOT_A_PITCH` | Это не стартап, а другая просьба (заявка 09 датасета) | Показать `message`, попросить питч |
| 422 | `PITCH_TOO_LONG` | Больше 4000 символов | Попросить сократить, не обрезать |
| 422 | `EMPTY_ANSWER` | Пустой ответ | Попросить ответить |
| 422 | `ANSWER_TOO_LONG` | Больше 2000 символов | Попросить сократить |
| 404 | `SESSION_NOT_FOUND` | Нет сессии или она чужая | Предложить начать заново |
| 409 | `SESSION_DONE` | Ответ в уже завершённый раунд | Показать итог через `GET` |
| 409 | `STEP_MISMATCH` | `step` не совпадает с текущим вопросом | Сделать `GET` и показать текущий вопрос |
| 429 | `RATE_LIMITED` | Слишком много запросов | Подождать `retryAfterSec` |
| 503 | `AI_UNAVAILABLE` | Модель не ответила, тайм-аут, квота, ответ не прошёл проверку | «Инвестор задумался», кнопка «Повторить» с тем же запросом. Питч и ответы сохранены |

Попытка выпросить балл (заявки 13, 14) и «игнорируй правила» — **не ошибки**: раунд идёт дальше,
в `notice` одна фраза, на оценку просьба не влияет.

Коды клиента без ответа сервера (`NETWORK`, `TIMEOUT`, `BAD_RESPONSE`) остаются внутренними
кодами бота и сайта, API их не отдаёт.

## 8. Правила API, которые проверяет оргкомитет

- **Ровно 5 вопросов и ровно 3 совета**, 10 критериев в порядке кейса — проверяет код, а не промпт.
- **Итог считает код** по формуле из раздела 5. Модель возвращает только уровни 0–3, цитаты и тексты.
- **Бот не врёт**: цитата `evidence` должна находиться в тексте питча или ответов, иначе уровень
  понижается до 0. Цифры и конкуренты — только из питча и ответов.
- **Совет отбраковывается**, если нет срока, срок дольше недели или есть стоп-фразы
  («проведите исследование рынка», «улучшите продукт», «наймите команду»).
- **Тайм-ауты**: вызов модели до 30 с, ответ API до 45 с, клиенты ждут до 60 с.
- **Лимиты**: не больше 10 новых сессий в час на `userId` и 60 запросов в минуту на IP.
- **Журнал без личных данных**: события `session_started`, `answered`, `result_shown {total}`,
  `round_started {round}` с `sessionId` и временем, без текстов питчей и ответов. Нужны для метрик (T29).
- **Хранение**: сессии переживают перезапуск API (файл или SQLite на сервере), хранятся 14 дней.

## 9. Моки и разработка без ядра

- `contract/examples/*.json` — по одному примеру каждого ответа и ошибки.
- `contract/mock-server.mjs` — HTTP-сервер этого контракта на заготовках, без модели и зависимостей:

  ```bash
  node contract/mock-server.mjs          # http://127.0.0.1:8080
  ```

  Сайт и бот разрабатываются против него (`TRAINER_API_URL=http://127.0.0.1:8080` для бота),
  потом тот же адрес занимает настоящий API T28. Мок понимает пустой питч, «не питч»,
  просьбу о балле, двойную отправку, чужую сессию и второй раунд.
