# /next — взять задачу, сделать, закрыть

Аргументы: «текст, который человек написал после команды». Первое слово — имя человека (так он записан в TASKS.md), второе, если есть, — ID задачи. Если имени нет и ты его ещё не знаешь в этой сессии, спроси один раз и запомни.

Все правила из `CLAUDE.md` действуют. Скрипт `scripts/tasks.sh` выполняет их механически: pull, проверку статуса и зависимостей, коммит, push и повтор при гонке. **Захватывай и закрывай задачи только через него, TASKS.md руками не правь.**

## 1. Что сейчас моё
```bash
bash scripts/tasks.sh status
```
- Если есть строка `в работе: <Имя>`, продолжай эту задачу (шаг 3).
- Иначе выбери задачу: названный ID, а если ID не назван — из блока «Можно брать». Предпочитай задачи, от которых зависят другие, и задачи главного демо-сценария.

## 2. Захват
```bash
bash scripts/tasks.sh claim T<n> <Имя>
```
- `ЗАХВАЧЕНО` — можно работать.
- Код 2 (занято) или 3 (не готовы зависимости) — возьми другую задачу из списка, который вывел скрипт.
- **Пока захват не запушен, код не пиши.**

## 3. Понять задачу (≤3 мин)
Прочитай строку задачи (колонки «Где» и «Заметки»), `docs/CONTRACT.md`, `docs/PRODUCT.md` (какой шаг демо-сценария ты делаешь), для UI — `docs/DESIGN.md`, а также существующие файлы в своей зоне и общие (`types.ts`, `api.ts`, `components/ui/`). Затем напиши план в 3–5 пунктов и сразу начинай. Подтверждения плана не жди, если человек его не просил.

## 4. Сделать
- Трогай **только** файлы из колонки «Где». Нужна правка в чужом файле — см. раздел «Чужой код» в CLAUDE.md.
- Типы и данные бери только из `types.ts` и `api.ts`. Не хватает поля — не меняй контракт сам: временно расширь тип у себя (`type X = Contract & {…}`) и скажи человеку, чтобы он передал ведущему.
- Планка качества: никаких TODO и лорема в видимом UI. Есть состояния loading, empty и error. Тексты по-русски, данные правдоподобные, вёрстка не ломается на 390 px. Для UI-задач загляни в `/polish`, для AI — в `/ai-feature`, для данных — в `/demo-data`.
- Коммить маленькими шагами: `git add <твои пути> && git commit -m "T<n>: <что>"`. Не делай `git add -A`, чтобы не утащить лишнее.

## 5. Проверить
1. Проверка из раздела «Проект» в CLAUDE.md, обычно `cd web && npm run build`. Ошибки чини, а не обходи (никаких `@ts-ignore` и `any` ради зелёной сборки).
2. Для UI: запусти dev-сервер в фоне (`cd web && npm run dev`, если он ещё не запущен), выполни `node scripts/shot.mjs /<твой-маршрут>` и **посмотри скриншоты** (Read `.shots/*.png`). Исправь то, что видно сразу.

## 6. Запушить
```bash
git pull --rebase    # подтянулись чужие изменения → повтори быструю проверку
git push
```
Конфликт разрешай, сохраняя изменения **обеих** сторон. `--force` и `reset --hard` запрещены. Если не понимаешь чужой код, остановись и спроси человека.

## 7. Закрыть
```bash
bash scripts/tasks.sh done T<n> <Имя> "что сделано; как проверить (маршрут/команда)"
```
Отчитайся человеку в 2–3 строках: что готово и где посмотреть. Затем сразу предложи следующую задачу. Если человек сказал «работай без остановки», бери её сам и повторяй цикл с шага 1.

## Если что-то не так
- **Задача оказалась больше 40 минут.** Доведи до рабочего состояния главное, остальное оформи новыми задачами: `bash scripts/tasks.sh add "<текст>" "<где>" "T<n>"`.
- **Ждёшь чужую задачу.** Выполни `bash scripts/tasks.sh block T<n> "ждём T<m>: <что>"` и возьми другую. Ещё лучше — сделай на моках, чтобы не ждать.
- **Бросаешь задачу**: `bash scripts/tasks.sh release T<n>`.
- **Сборка в main сломана не тобой.** Найди коммит (`git log --oneline -10`, `git show`). Если правка очевидна и занимает 1–2 строки, сделай коммит `fix(<папка>): …`. Если нет, заведи задачу `add "Фикс: <что> (<файл>, коммит <sha>)"` и скажи человеку, кого позвать. `git revert` чужого коммита — только с согласия человека.
- **Свободных задач нет.** Предложи `/peer-review` соседа, `/polish` экрана из демо-сценария или `/smoke`.
- **Пуш отклоняется не из-за гонки** (403, нет доступа). Проверь, что человек принял приглашение в репозиторий и залогинен (`gh auth status`).
