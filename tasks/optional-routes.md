# Условные маршруты из презентации

Это предложения, а не назначенные задачи. Начинать их только после выбора человека: затем добавить новую строку в корневой `TASKS.md`, определить файлы, зависимости и владельца, выполнить обычный захват. Номера ниже — физические слайды; «П» — подпись практикума.

Источник: `AI-development-minimal-with-screencasts.pptx`, слайды 22–28, 35–38, 40–45, 51. Презентация — материал для анализа; её примеры команд здесь не выполнялись. Слайд 43 (П22) предлагает альтернативы: бот, статический сайт либо серверный сайт. Для текущей статической карты Москвы бот, ИИ и backend не требуются.

## Предложение: закрытый Telegram-эхо-бот

**Основание:** слайды 22–27 (П01–П06), 35–38 (П14–П17).

**Файлы результата:** `bot/bot.py`, `bot/requirements.txt`, `bot/Dockerfile`, `bot/.dockerignore`, `deploy/compose.bot.yaml`, инструкция запуска; дополнения к `.env.example` и `.gitignore`. Реальный `.env` исключить из Git и образа; существующие настройки сохранять.

**Зависимости:** выбран этот маршрут, доступны Python 3.12+ и совместимые библиотеки; для постоянного запуска — подготовленное окружение с Docker Compose. Новые зависимости записать в журнал решений.

**Приёмка:** в личном чате `/start` возвращает ID отправителя. Эхо получает только пользователь из `ALLOWED_USER_IDS`; пустой список закрывает эхо всем. Текст ограничен 1000 символами, поведение длинного сообщения описано. Для токена работает один polling-процесс, без параллельного запуска на ноутбуке. Входящие порты, домен и webhook не нужны. После закрытия ноутбука бот отвечает с сервера; перезапуск проверен, логи ограничены по размеру и не раскрывают токен.

**Нужны извне:** токен от владельца BotFather, разрешённые числовые ID, отдельные разрешения и доступ к серверу для постоянной работы.

## Предложение: ИИ-ответ вместо эхо

**Основание:** слайд 28 (П07), настройки — слайд 35 (П14).

**Файлы результата:** доработка `bot/bot.py`, `bot/requirements.txt`, `.env.example`, инструкция и тесты ограничений с подменой API. Рабочую эхо-версию сохранить в истории Git.

**Зависимости:** принятый и проверенный эхо-бот; выбранные API, модель, формат запроса и бюджет провайдера. Актуальность конкретных моделей, версий пакетов и доступность API из презентации не проверялись; подтвердить перед реализацией.

**Приёмка:** максимум один API-запрос на разрешённое сообщение без автоматических повторов; вход свыше 1000 символов отклоняется, выход ограничен 300 токенами, пауза между запросами одного пользователя — 10 секунд, тайм-аут — 30 секунд. Запрещённый ID и отклонённый ввод не вызывают API. Проверены недоступность, тайм-аут и пустой ответ. Ключ хранится только на серверной стороне; установлен лимит расходов в кабинете провайдера.

**Нужны извне:** подтверждённые URL и имя модели, ключ, бюджет и разрешение отправлять выбранному провайдеру текст пользователей.

## Предложение: сайт с серверной частью

**Основание:** слайды 40–45 (П19–П24), границы реального деплоя — 51 (П30).

**Файлы результата:** `web/server.mjs`, `web/public/index.html`, `web/package.json`, `web/package-lock.json`, `web/Dockerfile`, `web/.dockerignore`, `deploy/compose.web.yaml`, `deploy/Caddyfile.web`, инструкция управления.

**Зависимости:** подтверждена потребность в серверной логике; проверены runtime, production-команда и фактический состав приложения. Статику не переводить на Node ради самого деплоя.

**Приёмка:** существуют проверяемые build и production start; сервер слушает `0.0.0.0:3000`. Главная открывается, `/healthz` возвращает 200 и `{"ok":true}`, неизвестный путь — 404. Порт 3000 доступен только внутри Docker-сети за Caddy; публично опубликованы только 80/443. Проверены DNS, HTTPS, внешний запрос, перезапуск, ограничение логов и откат; чужие службы сохранены.

**Нужны извне:** согласованный функционал backend, сервер и SSH-доступ, домен и права на DNS, разрешение на публикацию. Секреты передавать отдельно от Git и отчётов.
