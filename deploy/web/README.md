# Подключение сайта и Telegram-бота к одному API

Workflow `connect-trainer` запускается вручную. Сначала `mode=probe`: только состояние служб,
порты, health и безопасные параметры окружения на обоих серверах. `mode=connect` разворачивает
общее ядро из текущего коммита и переключает оба интерфейса после проверок.

## Адреса и секреты

- Сайт: `SITE_SERVER_HOST`, `SITE_SERVER_USER`, необязательный `SITE_SERVER_PORT` (22),
  Actions Secret `SITE_SERVER_PASSWORD`.
- Бот: `BOT_SERVER_HOST`, `BOT_SERVER_USER`, необязательный `BOT_SERVER_PORT` (22),
  Actions Secret `BOT_SERVER_PASSWORD`.
- Ключ Gemini берётся из `/etc/fightinvestor.env` на сервере сайта и передаётся через SSH stdin
  в `/etc/investor-api/api.env` на сервере бота. Оба файла доступны только root. Ключ не пишется
  в файлы runner, Git, артефакты или вывод workflow.
- `BOT_TELEGRAM_TOKEN` не читается workflow и не заменяется. В существующем
  `/etc/investor-bot/bot.env` меняется только `TRAINER_API_URL`.
- После успешного connect установить repository Variable
  `TRAINER_API_URL=http://127.0.0.1:8080`, чтобы будущий `deploy-bot` сохранил подключение.

SSH проверяет сохранённые ED25519 fingerprints обоих серверов. Для сайта отпечаток получен
при первом SSH-входе, для бота — из успешного `deploy-bot` probe run `42251580842`.
Смена ключа хоста требует отдельной сверки, скрипт не принимает новый ключ автоматически.

## Схема

```
браузер → nginx на сервере сайта → gateway 127.0.0.1:8787
                                 → SSH tunnel 127.0.0.1:18080
                                 → API 127.0.0.1:8080 на сервере Ивана
Telegram → существующий investor-bot → тот же API 127.0.0.1:8080
```

API слушает только loopback. Ключ туннеля создаётся на сервере сайта и никогда его не покидает.
Отдельный пользователь на сервере бота допускает только SSH forwarding к `127.0.0.1:8080`
с IP сайта; shell, PTY, remote forwarding и пароль отключены. Root SSH не меняется.

API работает под `investorapi`, записи — `/var/lib/investor-api`, код —
`/opt/investor-api/releases/<commit>`. Gateway работает под `fightinvestor`, код —
`/opt/fightinvestor/releases/<commit>/web`. Его отдельный env-файл содержит только настройки
gateway и `WEB_COOKIE_SECRET`; ключ Gemini в процесс gateway не передаётся.

`AI_FALLBACK=off` исключает незаметную подмену ответа модели демозаготовками. `health.mode=live`
подтверждает режим и наличие ключа, но не подтверждает квоту или успешную генерацию Gemini.
Проверки деплоя не отправляют питчи модели.

## Порядок и откат

1. Проверка fingerprints, состояния существующего бота и занятости порта 8080.
2. API выкатывается отдельной службой, получает ключ и проходит health/persona.
3. Создаётся закрытый SSH-туннель, проверяется доступность API через него.
4. Gateway и шесть публичных файлов сайта переключаются с сохранением предыдущей версии.
5. Только после этого меняется `TRAINER_API_URL` существующего бота; его health проверяется.

При неудаче API восстанавливается прежний API unit/env, если они были. Неудачное переключение
сайта восстанавливает предыдущий unit и публичные файлы из `/var/backups/fightinvestor/<commit>`.
Неудачный health бота возвращает его прежнее окружение. Сессии API не удаляются, исходники
бота и его токен не заменяются. При частичной неудаче нужно прочитать последний успешный шаг:
уже проверенный API и туннель могут остаться запущенными.

DNS/HTTPS этот workflow не изменяет. До делегирования домена сайт проверяется по HTTP/IP.

Проверка инфраструктурных файлов: `bash -n deploy/web/*.sh` (каждый файл отдельно).
Workflow перед connect запускает тесты ядра, API и gateway.
